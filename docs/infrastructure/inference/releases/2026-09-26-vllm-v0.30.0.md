# 2026-09-26 vLLM v0.27.1 → v0.30.0

**Status:** in progress
**Profiles affected:** fast, main
**Window:** main-model restart announced separately (about 5 min downtime per restart)

## Change

| | Before | After (stage 2–3) |
|---|---|---|
| Image | `vllm/vllm-openai:v0.27.1-aarch64-cu129` | `vllm/vllm-openai:v0.30.0-aarch64` (CUDA 13.0) |
| Flags | `--moe-backend marlin` | unchanged (MoE backend is a later, separate stage) |
| Config | — | unchanged |

Findings changed the image target from the original cu129 plan. The
`v0.30.0-aarch64-cu129` tag cannot start: torch 2.14.0+cu130 ships against
torchvision 0.28.0+cu129, and `vllm` dies on import with
`RuntimeError: operator torchvision::nms does not exist`.
`image_preflight.sh` reported every requested flag "NOT FOUND" for this
image, because it did not check whether `vllm serve --help=all` itself had
crashed rather than simply omitting the flag — fixed to fail loudly
(roadmap 0.5) before this preflight is rerun. The working tag is
`v0.30.0-aarch64` (CUDA 13.0), which is also what unlocks FlashInfer GDN
prefill on SM12x (#55715): the CUDA bump is no longer a side effect to
avoid, it is required.

## Why

Two main-engine incidents on 2026-09-25: an Xid 13 fault, then a silent
EngineCore stall (`docs/troubleshooting/vllm-main-engine-hang-gb10.md`).
v0.30.0 brings SM12x/GB10 work: FlashInfer GDN prefill on SM12x (#55715),
startup warmup of Qwen3.5 GDN kernels (#54797, #54251), and SM12x FP8 fixes
(#55180). It also includes sleep-mode fixes (#51485, #52957, #53507, #53508).

The original proposal was `--moe-backend b12x`, with `--cudagraph-mode PIECEWISE`
as the fallback. Research and preflight changed that:

- `b12x` is a valid v0.30.0 MoE backend, but it needs the optional
  `b12x==1.3.0` package (`vllm[b12x]`). The official image does not install it,
  so the engine would refuse to start. The package describes itself as not
  intended for production.
- `flashinfer_b12x` is bundled (FlashInfer CuteDSL). Upstream has an open Xid 31
  report for it on Qwen3.5 NVFP4 (#50189). This is a candidate for a later
  flag-only stage.
- `--cudagraph-mode` is not a CLI flag. The equivalent is
  `--compilation-config '{"cudagraph_mode":"PIECEWISE"}'`. Upstream #54331
  reports PIECEWISE also failing for hybrid-GDN NVFP4 under load, with only
  eager mode surviving.
- None of the upstream issues that match our stall (#52225 Marlin NVFP4 Xid 13,
  #52247 EngineCore blocks forever, #54225 FlashInfer + fp8 KV on this exact
  checkpoint) is fixed in v0.30.0. This upgrade is not expected to fix the
  stall by itself. The soak gate is what shows whether it did.
- v0.30's own `vllm bench` counts client queue time in TTFT (#54136). Our
  harness is version-independent, so its numbers compare across versions.

## Risks and rollback

- Rollback: revert the stage commit. The v0.27.1 image stays cached on sparky.
- New behaviour in v0.30: W4A4 NVFP4 is now preferred on SM12x (#55170). This
  does not affect us, because we pin `--moe-backend marlin`.

## Stages

0. Preflight `v0.30.0-aarch64-cu129`: **FAILED** 2026-09-29. `vllm` dies on
   import (`torchvision::nms does not exist`: torch 2.14.0+cu130 with
   torchvision 0.28.0+cu129). Image unusable.
0b. Preflight `v0.30.0-aarch64` (cu130): **PASSED** 2026-09-30 for every
   flag the main engine uses today, and for stages 1.2-1.4:

   | Flag | Result |
   |---|---|
   | `--async-scheduling` | accepted |
   | `--speculative-config`, `--spec-method=qwen3_5_mtp` | accepted |
   | `--kv-cache-memory-bytes` | accepted |
   | `--attention-backend=flashinfer` | flag accepted; v0.30.0's help no longer enumerates backends, so the value is not validated by preflight |
   | `--gdn-prefill-backend=flashinfer` | accepted (new in this release line; the SM12x FlashInfer GDN prefill switch) |
   | `--moe-backend=marlin` | accepted |
   | `--tool-call-parser=qwen3_xml` | accepted |
   | `--reasoning-parser=qwen3` | flag accepted; parsers no longer enumerated in help |
   | `--enable-sleep-mode`, `--long-prefill-token-threshold` | accepted |
   | `--load-format=fastsafetensors` | **NOT FOUND** in v0.30.0, and also absent from v0.27.1's choices: the model card's value never applied to upstream images |
   | `--load-format=instanttensor` | accepted: the replacement (InstantTensor, "distributed loading with pipelined prefetching and fast direct I/O") |

   Package set: vllm 0.30.0, torch 2.13.0+cu130, torchvision 0.28.0+cu130,
   torchaudio 2.11.0+cu130, FlashInfer 0.6.18.post1, transformers 5.17.0,
   CUDA 13.0. Image cached on sparky (9.69 GB; the Docker Hub pull took over
   an hour because the host's resolver intermittently timed out on
   `registry-1.docker.io`).
1. Baselines on v0.27.1 (fast, main): **done** 2026-09-30,
   `benchmarks/main/20260930T2202Z_baseline-v0.27.1.json` and
   `benchmarks/fast/20260930T2226Z_baseline-v0.27.1.json`, both promoted.
2. fast → v0.30.0: **FAIL by the thresholds, kept with reason** 2026-10-01
   (`benchmarks/fast/20261001T0409Z_candidate-v0.30.0.json`, re-run
   `20261001T0418Z_candidate-v0.30.0-rerun.json`). FlashInfer GDN prefill
   selected on SM12x. Against the v0.27.1 baseline: TTFT p50 -25% to -79%
   across scenarios, aggregate throughput +27% at c=4 and +24% at c=8, ITL
   p95 -41% / -36% at c=4 / c=8, soak 300 s at c=8: 656 requests, 0
   errors, 0 stalls, sleep/wake sane. The FAIL is one metric,
   `c1_prefill_8k.itl_p95_ms`: 15.8 -> 20.2 ms, and 35.4 ms on the re-run,
   i.e. one or two slow decode steps right after an 8k prefill in a
   32-token sample (p50 unchanged at 11.5 ms). Operator decision: a jitter
   tail on an eager-mode 0.8B canary that cannot exercise CUDA graphs does
   not block the stage; the main engine's own benchmark decides. Promoted
   as the fast baseline so later fast stages compare against v0.30.0.
3. main → v0.30.0: **FAIL, reverted** 2026-10-01
   (`benchmarks/main/20261001T0437Z_candidate-v0.30.0.json`). Serving was
   faster: TTFT p50 -35% at c=1 short, -19% at 8k prefill, -15% at 32k,
   -23% at c=4; aggregate throughput +4-5%; init 52 s instead of 155 s
   (torch.compile 15 s). But the 600 s soak at c=4 had a max end-to-end of
   36.2 s against 12.5 s on the baseline (p99 31.0 s, +148%) and one minute
   with 25% fewer output tokens: a silent 15-20 s pause with no recompile,
   autotune, preemption or JIT warning in the engine log. That is the GB10
   stall family in miniature and the soak gate exists for it. Also
   `c1_prefix_hit_8k.itl_p95_ms` +32% (same post-prefill jitter tail as
   the fast canary). Reverted to v0.27.1 (image cached); the fast canary
   stays on v0.30.0. Next: stage 1.1b, v0.30.0 with
   `--gdn-prefill-backend triton` (the new FlashInfer GDN prefill kernel is
   the main difference on the hot path), then the remaining backstops.
4. (separate change) main `--moe-backend flashinfer_b12x` against the stage-3 baseline: *not scheduled*

Consequences for the roadmap's Phase 1 stages: 1.5 must use
`--load-format instanttensor`, not `fastsafetensors`; 1.1 may add
`--gdn-prefill-backend flashinfer` as its own flag stage rather than
relying on auto-selection.

## Findings during preparation

- Since v0.30.0, `vllm serve --help=all` infers the device type while
  building the argument parser and fails on a CPU-only pod ("Failed to
  infer device type"). The preflight pod now requests one time-sliced GPU
  and the nvidia runtime class.

- sparky `/etc/hosts` held a hand-added "kubani temp" block from 2026-08-16
  that pinned Docker Hub to IPs Docker no longer serves, so every Docker Hub pull
  on sparky failed TLS. The block was removed (backup at
  `/etc/hosts.bak.20260926`) and pulls work again through DNS.
- Both gpu-brokers had a leaked in-flight counter (1 with nothing running),
  which blocked auto-sleep and manual sleep. Broker pods restarted on
  2026-09-26. Root cause is in kubani-gpu-broker `proxy.py`: in the streaming
  `finally`, `await upstream.aclose()` comes before `_finish()`, so if a client
  disconnect cancels the task during `aclose()`, the release is skipped.
- The fast model emits Qwen3 XML tool calls, but it runs
  `--tool-call-parser hermes`, so its tool calls arrive as plain text. This is
  outside the scope of this change.
