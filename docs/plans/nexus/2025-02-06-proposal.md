# Kubani Nexus: An Architecture for a Safer, Always-On Conversational Agent

**Author:** Manus AI
**Date:** February 6, 2026

## 1. Introduction

This document presents a comprehensive architectural proposal for **Kubani Nexus**, a next-generation autonomous agent system designed to operate continuously and safely within the existing `kubani` Kubernetes cluster. The proposed design synthesizes the most effective patterns from OpenClaw, NanoClaw, and the robust infrastructure of the `kubani` project itself. Nexus is envisioned as a central, conversational intelligence that unifies and extends the cluster's capabilities, replacing the existing `k8s-monitor` and `news-digest` syndicates with a more powerful, interactive, and cohesive system.

The core objective is to create an agent that is not only highly capable—engaging in back-and-forth dialogue, managing its own memory, exploring the web, and executing complex tasks—but also fundamentally secure, observable, and maintainable. By leveraging the mature, skills-centric framework already present in `kubani`, and integrating best-of-breed patterns for agentic orchestration, Nexus will provide a streamlined and powerful platform for human-AI collaboration.

This proposal outlines a system that is:

*   **Conversational and Interactive:** Engaging users through both Discord and the existing Kubani web UI.
*   **Durable and Always-On:** Leveraging Temporal workflows for resilient, long-running execution.
*   **Secure and Sandboxed:** Building upon the containerized execution model and introducing new safety layers inspired by OpenClaw.
*   **Modular and Extensible:** Embracing a skills-centric architecture that promotes reusability, testability, and dynamic capability expansion.
*   **Integrated and Efficient:** Deeply integrating with the cluster's existing MCP servers, databases, and LLM infrastructure.

## 2. Core Architectural Philosophy: A Syndicate of Specialists

At the heart of the Nexus architecture is the **Syndicate of Specialists** model. Instead of a single, monolithic agent attempting to perform all functions, Nexus will operate as a top-level orchestrator—a **Nexus Syndicate**—that delegates tasks to a collection of smaller, specialized agents. This approach, inspired by the `kubani` framework's own `k8s-monitor` and `learning_system` syndicates, provides significant advantages in terms of modularity, scalability, and maintainability.

The central **Nexus Syndicate** will be implemented as a long-running Temporal workflow. This provides several critical benefits:

1.  **Durability:** The agent's state and ongoing tasks persist across pod restarts and cluster events. The agent is truly 

"always-on."
2.  **Observability:** All agent actions, decisions, and state transitions are recorded in the Temporal UI, providing a complete audit trail.
3.  **Scalability:** Complex tasks can be broken down into child workflows or activities that run in parallel, managed by Temporal.

The Nexus Syndicate will replace the existing `k8s-monitor` and `news-digest` syndicates. Their functionality will be absorbed and enhanced by Nexus, which will be able to perform those tasks and much more, all through a unified conversational interface. For example, instead of a static daily news digest, a user could ask Nexus, "What are the latest developments in AI hardware?" or "Summarize the Kubernetes cluster status over the last 24 hours and highlight any anomalies."

## 3. System Components

The Nexus architecture is composed of several key components that work together to provide a robust and flexible agent system.

| Component | Technology | Purpose |
| :--- | :--- | :--- |
| **Nexus Syndicate** | Temporal Workflow | The central, always-on orchestrator that manages the agent's lifecycle, delegates tasks, and maintains state. |
| **Conversational Gateway** | Python (FastAPI/WebSockets) | A new service that acts as a bridge between user interfaces (Discord, Kubani UI) and the Nexus Syndicate. |
| **Agent Core** | Strands Agents SDK | The execution engine for specialized agents, responsible for interpreting prompts, selecting skills, and running tools. |
| **Execution Sandbox** | Docker Containers | Secure, isolated environments for executing skills and tools, preventing unintended side effects. |
| **Unified Memory** | Qdrant, Neo4j, Redis | A multi-layered memory system for long-term knowledge, episodic memory, and short-term context. |
| **UI & Observability** | Kubani UI (React/Rust) | The existing web interface, enhanced with new features for monitoring and interacting with the Nexus agent. |

### 3.1. Nexus Syndicate: The Durable Orchestrator

The Nexus Syndicate is the heart of the system. It is a long-running Temporal workflow that represents the agent's core consciousness. It is responsible for:

*   **Receiving tasks** from the Conversational Gateway.
*   **Maintaining conversational context** and long-term goals.
*   **Planning and decomposing** complex tasks into smaller steps.
*   **Delegating** those steps to specialized agents (run as Temporal activities).
*   **Aggregating results** and formulating responses.

By modeling the agent's main loop as a Temporal workflow, we gain immense resilience. The agent can survive cluster updates, pod failures, and network partitions without losing its train of thought.

### 3.2. Conversational Gateway: The Unified Interface

To facilitate real-time, back-and-forth conversation, a new **Conversational Gateway** service will be introduced. This service will:

*   **Connect to the Discord MCP Server** to send and receive messages.
*   **Expose a WebSocket endpoint** for the Kubani UI to connect to.
*   **Normalize incoming messages** from different sources into a standard format.
*   **Use Temporal signals** to send user messages to the running Nexus Syndicate workflow.
*   **Subscribe to a Redis Pub/Sub channel** to receive real-time responses from the agent and forward them to the appropriate user interface.

This gateway decouples the user-facing interfaces from the agent's core logic, allowing for a more responsive and interactive experience.

### 3.3. Agent Core: The Skills-Centric Executor

Each specialized agent within the syndicate (e.g., a `KubernetesToolAgent`, a `WebSearchAgent`) will be built using the **Strands Agents SDK**. This aligns with the `kubani` project's existing patterns and provides a powerful, model-driven execution engine. The key principle here is that agents are **thin orchestrators** that delegate all meaningful work to **skills**.

This approach, heavily inspired by ADR-007 in the `kubani` docs, makes the system:

*   **More modular:** Logic is encapsulated in discrete, reusable skills.
*   **Easier to test:** Skills can be tested in isolation.
*   **More flexible:** New capabilities can be added simply by creating new skills.

### 3.4. Execution Sandbox: A Secure Environment

Safety is a paramount concern. Drawing inspiration from both OpenClaw's sandboxing and NanoClaw's container-per-agent model, all skill and tool execution will occur within a secure **Execution Sandbox**. This will be implemented using Docker containers, with a minimal, hardened base image.

Key security features will include:

*   **Filesystem Isolation:** Agents will only have write access to a dedicated, ephemeral workspace. Access to other parts of the filesystem will be strictly controlled and read-only.
*   **Network Policies:** By default, sandboxes will have no network access. Skills that require internet access (e.g., for web browsing) must explicitly declare it, and will be subject to additional scrutiny.
*   **Resource Limits:** CPU and memory limits will be enforced on all sandboxes to prevent resource exhaustion.
*   **AST-based Shell Parsing:** For shell commands, we will adopt OpenClaw's pattern of parsing the Abstract Syntax Tree (AST) to block dangerous operations like command substitution and redirection, rather than relying on simple blocklists.

### 3.5. Unified Memory: The Agent's Brain

The agent's ability to learn and maintain context over time is critical. We will leverage and unify the `kubani` cluster's existing data stores to create a powerful, multi-layered memory system:

*   **Long-Term Knowledge (Neo4j):** The existing Neo4j graph database will be used to store structured knowledge about entities and their relationships (e.g., "Pod A is running on Node B").
*   **Episodic & Semantic Memory (Qdrant):** The Qdrant vector database will store conversational history, documents, and other unstructured data, enabling semantic search and retrieval-augmented generation (RAG).
*   **Working Memory (Redis):** Redis will be used for short-term memory, such as caching recent conversation turns and managing the agent's immediate context window.

The existing **Memory MCP Server** will be the primary interface for the agent to interact with this unified memory system.

### 3.6. UI & Observability: A Window into the Agent

The existing Kubani UI will be extended to become the primary monitoring and administration interface for Nexus. New UI components will be added to:

*   **Display real-time conversation logs** from Discord and the UI itself.
*   **Visualize the agent's status,** current job, and recent actions.
*   **Browse and manage the agent's memory,** allowing for manual inspection and correction.
*   **Review and approve** actions that require human-in-the-loop (HITL) confirmation.

This will be powered by the UI's existing Rust/Axum backend, which will subscribe to the same Redis event streams as the Conversational Gateway to receive real-time updates from the agent.

## 4. Key Architectural Patterns

This proposal is built upon several powerful architectural patterns that have proven effective in modern agentic systems.

### 4.1. Skills-Centric Architecture

As established in the `kubani` project, the system will be fundamentally **skills-centric**. All agent capabilities, from checking Kubernetes pod status to browsing the web, will be implemented as skills that adhere to the **Agent Skills standard**. This ensures that the system is modular, extensible, and that capabilities can be tested and versioned independently.

### 4.2. Conversational Hot-Reloading: A Safer Approach

OpenClaw's ability to write its own skills at runtime is incredibly powerful, but also presents a significant security risk. We will adopt a safer, more controlled version of this pattern: **Conversational Hot-Reloading**.

Instead of allowing the agent to directly write to its own skill directory, the agent will:

1.  **Propose a new or modified skill** as a code block in the conversation.
2.  **Require human approval** for the change via the Kubani UI or a Discord reaction.
3.  Upon approval, a separate, privileged **Skill Manager** service will write the new skill file to the appropriate directory.
4.  The **Skill Registry** will detect the change and make the new skill available to the agent.

This maintains the spirit of self-improvement and dynamic extension, while inserting a critical human-in-the-loop checkpoint to prevent the agent from introducing malicious or unstable code.

### 4.3. Layered Security Model

Security is not a single feature, but a series of layers. Nexus will employ a defense-in-depth strategy:

| Layer | Description |
| :--- | :--- |
| **1. Human-in-the-Loop (HITL)** | Critical actions (e.g., modifying cluster resources, creating new skills) will require explicit user approval. |
| **2. AST Shell Guard** | Shell commands will be parsed to prevent dangerous syntax before execution. |
| **3. Sandbox Isolation** | All code execution is confined to ephemeral Docker containers with strict filesystem, network, and resource constraints. |
| **4. Least Privilege Principle** | The agent itself, and all its components, will run with the minimum permissions necessary to perform their functions. |

## 5. Development and Testing Workflow

A streamlined and efficient development workflow is a primary requirement. We will leverage and enhance the existing tools in the `kubani` project to create a simple, powerful inner loop for developers.

### 5.1. Local Development with Cluster Services

Developers will be able to run the Nexus agent on their local machine while still connecting to the services running in the `kubani` cluster (Temporal, Qdrant, etc.). This is achieved by running a local instance of the Conversational Gateway and the Nexus Syndicate, which then connect to the cluster's MCP servers. This provides a realistic development environment without the need to run the entire infrastructure stack locally.

### 5.2. Hot-Reloading for Rapid Iteration

The agent and its skills will support **hot-reloading**. When a developer saves a change to a skill file or the agent's source code, the system will automatically reload the new code without requiring a full restart. This enables rapid iteration and testing.

### 5.3. Automated Testing and Evaluation

We will build a comprehensive suite of automated tests, including:

*   **Unit tests** for individual skills and components.
*   **Integration tests** that verify the interaction between different parts of the system.
*   **End-to-end evaluation suites** that run the agent through a series of realistic scenarios and evaluate its performance against a set of predefined metrics.

This will ensure that new changes are safe and effective before they are deployed to the cluster.

## 6. Proposed Changes to Kubani Cluster

This architecture is designed to leverage the existing `kubani` infrastructure as much as possible. However, a few changes are proposed:

*   **Deploy a new Conversational Gateway service.**
*   **Deploy a new Skill Manager service.**
*   **Decommission the existing `k8s-monitor` and `news-digest` deployments,** as their functionality will be absorbed by Nexus.
*   **Enhance the Kubani UI** with the new monitoring and interaction features.

No new databases or core infrastructure services are required. The proposal focuses on building a more intelligent and interactive application layer on top of the powerful foundation that already exists.
